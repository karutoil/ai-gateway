# LANGFUSE

## 1. Trace-level observability

**Data model.** `Observations` are the individual steps (LLM calls, tool calls, retrieval steps); they nest arbitrarily and carry an observation type. A `trace` is "the logical grouping of all observations that share the same `trace_id`". Trace-level attributes (`user_id`, `session_id`, `tags`, `metadata`) "live on every observation within the trace; the SDKs propagate them automatically" — Langfuse stores **one wide observations table**, each row holding observation data plus a copy of the trace-level attributes, "This keeps queries and aggregations fast" ([data-model](https://langfuse.com/docs/observability/data-model)). Trace-level metrics in v4 are derived, e.g. "counting distinct trace IDs rather than counting rows in a traces table" ([dashboard-changes-in-v4](https://langfuse.com/faq/all/dashboard-changes-in-v4)).

**Observation types (10):** `event`, `span`, `generation`, `agent`, `tool`, `chain`, `retriever`, `evaluator`, `embedding`, `guardrail` — `generation` and `embedding` carry model/token/cost data ([observation-types](https://langfuse.com/docs/observability/features/observation-types)). Set via `as_type` (Python) / `asType` (TS); Python SDK ≥3.3.1, TS SDK ≥4.0.0 ([observation-types](https://langfuse.com/docs/observability/features/observation-types)).

**Nesting depth.** No documented cap on nesting depth. Agent graphs render two ways over the same trace — **Aggregated** (one node per unique step name, repeated calls collapsed with a counter e.g. `retrieve_docs (3/3)`, loops drawn as cycles) and **Expanded** (one node per individual call, loops unrolled into a DAG) ([agent-graphs](https://langfuse.com/docs/observability/features/agent-graphs)). Graphs appear automatically when a trace contains any observation type other than `span`/`event`/`generation`, or via the LangGraph integration ([agent-graphs](https://langfuse.com/docs/observability/features/agent-graphs)).

**Sessions.** `sessionId` groups traces for multi-turn interactions, gives a session replay view; must be US-ASCII <200 chars (longer is dropped); propagated via `propagate_attributes(session_id=...)` / `propagateAttributes({sessionId})` ([sessions](https://langfuse.com/docs/observability/features/sessions)). Sessions aggregate `Session 1 o-- n Trace` ([data-model](https://langfuse.com/docs/observability/data-model)). Sessions have **no dedicated API endpoint** in v2 — fetch observations sharing a `sessionId` and group client-side ([query-via-sdk](https://langfuse.com/docs/api-and-data-platform/features/query-via-sdk)).

**Users.** `userId` (username/email/any unique id) propagated the same way; drives "aggregating metrics such as LLM usage cost by `userId`" plus an all-users view and per-user view ([users](https://langfuse.com/docs/observability/features/users)).

**Tags.** Strings ≤200 chars, multiple per observation; "the full set of tags applied across all observations in a trace" is the trace's tags. Filterable in tables and the search bar (`tags:(billing AND urgent)`); usable to "Segment custom dashboards and metrics by tag". **Tags are immutable** — cannot be added/edited in the UI after creation ([tags](https://langfuse.com/docs/observability/features/tags)).

**Metadata.** Propagated key-value pairs; values limited to ≤200-char strings, "Keys are limited to alphanumeric characters only", over-length values dropped; filterable by metadata keys in UI and API ([metadata](https://langfuse.com/docs/observability/features/metadata)).

**Release / version.** `release` = overall application version (semver or git commit hash); `version` = per-observation/component version (e.g. an object named `guess-countries` at `1.0` vs `1.1`). Release resolution order: explicit arg → `LANGFUSE_RELEASE` env → auto-detected Vercel/Heroku/Netlify env vars. Both are dashboard/metric dimensions ([releases-and-versioning](https://langfuse.com/docs/observability/features/releases-and-versioning)).

**Environments.** `environment` is available on all events; the UI environment filter "applies across all views in Langfuse". Created on first ingestion, persistent, **cannot be deleted or renamed via the UI**. Must match `^(?!langfuse)[a-z0-9-_]+$`, ≤40 chars; default `default`; set via `LANGFUSE_TRACING_ENVIRONMENT` or per-request with `propagate_attributes(environment=...)` ([environments](https://langfuse.com/docs/observability/features/environments)).

**Search/filter.** A filter search bar parses one line into the same filter state as the sidebar, with autocomplete and URL serialization (shareable links). Syntax: `field:value`, `latency:>2`, `cost:>=0.01`, `startTime:>2026-06-01`, wildcards (`name:*checkout*`, `checkout*`, `*checkout`, `=checkout` for exact), negation (`-environment:production`), any-of/all-of (`level:(ERROR OR WARNING)`, `tags:(billing AND urgent)`), nested metadata/scores (`metadata.region:eu`, `scores.accuracy:>0.8`, `scores.helpfulness:positive`, `scores."Answer Relevance":>=0.9`), null checks (`has:endTime`, `-has:endTime`), and full-text search with `input:`/`output:` scoping ([filter-search-bar](https://langfuse.com/docs/observability/features/filter-search-bar)). Full-text search covers ids, names, input, output; matching is case-insensitive and whole-word ([full-text-search](https://langfuse.com/docs/observability/features/full-text-search), [filter-search-bar](https://langfuse.com/docs/observability/features/filter-search-bar)). Facet counts in the sidebar "are computed against the filters you already have active" ([filter-search-bar](https://langfuse.com/docs/observability/features/filter-search-bar)).

**Root observations.** v4 applies `Is Root Observation = true` by default in the observations table; it includes **outer roots** (no parent) and **app roots** (highest exported app observation when an OTEL/infra span is the outer parent) ([explore-observations-in-v4](https://langfuse.com/faq/all/explore-observations-in-v4)).

**Other trace-level features (fetched, listed for completeness):** trace IDs & distributed tracing with custom `trace_id`/tracer IDs ([trace-ids-and-distributed-tracing](https://langfuse.com/docs/observability/features/trace-ids-and-distributed-tracing)); comments on traces/observations/sessions/prompts ([comments](https://langfuse.com/docs/observability/features/comments)); corrections ([corrections](https://langfuse.com/docs/observability/features/corrections)); user feedback ([user-feedback](https://langfuse.com/docs/observability/features/user-feedback)); log levels ([log-levels](https://langfuse.com/docs/observability/features/log-levels)); Pulse outlier strip ([pulse](https://langfuse.com/docs/observability/features/pulse)); sampling ([sampling](https://langfuse.com/docs/observability/features/sampling)).

**Freshness.** "New data is typically available for querying within 15-30 seconds of ingestion" ([query-via-sdk](https://langfuse.com/docs/api-and-data-platform/features/query-via-sdk)). Older SDKs (`langfuse-python` < 4.7.0, `langfuse-js` < 5.4.0) or OTEL exporters without `x-langfuse-ingestion-version: 4` can be delayed "up to 15 minutes on v2 endpoints"; the inpestion intro says other public API endpoints can delay ~10 minutes ([metrics-api](https://langfuse.com/docs/metrics/features/metrics-api), [public-api](https://langfuse.com/docs/api-and-data-platform/features/public-api)).

## 2. Dashboard charts and breakdowns

### 2a. Metrics API v2 — the authoritative metric/dimension surface

`GET /api/public/v2/metrics`, query passed as a JSON string ([metrics-api](https://langfuse.com/docs/metrics/features/metrics-api)). Available in **all Cloud plans and self-hosted v4+**; on self-hosted v3 use v1 ([metrics-api](https://langfuse.com/docs/metrics/features/metrics-api)).

**Views (4):** `observations`, `scores-numeric`, `scores-categorical`, `scores-boolean`. "The `traces` view is no longer available in v2" ([metrics-api](https://langfuse.com/docs/metrics/features/metrics-api)).

**`observations` dimensions:** `environment`, `type`, `name`, `level`, `version`, `tags`, `release`, `traceName`, `traceRelease`, `traceVersion`, `providedModelName`, `promptName`, `promptVersion`, `isRootObservation`, `startTimeMonth` (YYYY-MM) ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

**`observations` measures:** `count`, `latency`, `streamingLatency`, `inputTokens`, `outputTokens`, `totalTokens`, `outputTokensPerSecond`, `tokensPerSecond`, `inputCost`, `outputCost`, `totalCost`, `timeToFirstToken`, `countScores` ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

**`scores-numeric` / `-boolean` / `-categorical` dimensions:** `environment`, `name`, `source` (API/ANNOTATION/EVAL), `dataType` (NUMERIC/BOOLEAN), `configId`, `timestampMonth`, `timestampDay`, `value`, `traceName`, `tags`, `traceRelease`, `traceVersion`, `observationName`, `observationModelName`, `observationPromptName`, `observationPromptVersion`; `scores-boolean` adds `booleanValue`; `scores-categorical` uses `stringValue` instead of `value` ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)). Score measures: `count`, `value`; for boolean, "`avg` returns the true-rate" ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

**Aggregations (11):** `sum`, `avg`, `count`, `max`, `min`, `p50`, `p75`, `p90`, `p95`, `p99`, `histogram` ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

**Time granularities (6):** `auto`, `minute`, `hour`, `day`, `week`, `month`; `auto` "bins the data into approximately 50 buckets based on the time range" ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

**High-cardinality dimensions that cannot be grouped:** observations view — `id`, `traceId`, `userId`, `sessionId`, `parentObservationId`; score views — `id`, `traceId`, `userId`, `sessionId`, `observationId`. "These dimensions remain available for filtering." ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml), [metrics-api](https://langfuse.com/docs/metrics/features/metrics-api)). v4 additionally requires a row limit + sort order ("top 20 users by cost, descending") for high-cardinality grouping, and "Time-series charts cannot use high-cardinality dimensions at all" ([dashboard-changes-in-v4](https://langfuse.com/faq/all/dashboard-changes-in-v4)).

**Filter operators by type** (from the query schema): datetime `>`, `<`, `>=`, `<=`; string `=`, `contains`, `does not contain`, `starts with`, `ends with`; stringOptions `any of`, `none of`; arrayOptions `any of`, `none of`, `all of`; number `=`, `>`, `<`, `>=`, `<=`; stringObject/numberObject same as string/number with a required `key`; boolean `=`, `<>`; null `is null`, `is not null`. Filter value types: `datetime`, `string`, `number`, `stringOptions`, `categoryOptions`, `arrayOptions`, `stringObject`, `numberObject`, `boolean`, `null` ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

**Limits:** default `config.row_limit` 100, max 1,000; histogram `bins` 1–100, default 10. Order by `{aggregation}_{measure}` e.g. `sum_totalCost`, or `time_dimension` ([metrics-api](https://langfuse.com/docs/metrics/features/metrics-api), [openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

**Latency/throughput measures available:** `latency` (ms), `timeToFirstToken` (ms, TTFT), `streamingLatency` (completion start→end, ms), `outputTokensPerSecond`, `tokensPerSecond`, plus `p50/p75/p90/p95/p99` aggregations on any measure ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)).

### 2b. Custom dashboards

**Widget configuration axes:** Data Source (traces, observations, or scores — numeric, categorical, or boolean) → Metrics (count, latency, cost, scores) → Dimensions (group by user, model, time, trace name, …) → Filters → Chart Type ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards)).

**Chart types:** Line, Bar, Time Series, Pie in the docs page ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards)); the in-table chart builder offers **Line, Area, Bars, Ranked, Pie, Number** ([events-table-charts](https://langfuse.com/docs/observability/features/events-table-charts)).

**Chart-any-table (Visualize panel):** Metric ∈ {Count, Latency, Cost, Tokens}; Aggregation depends on metric — Count is always counted; Latency supports Average, Median (p50), p95, p99, Max, Min; Cost and Tokens support Sum, Average, p95, Max. Breakdown options are **Total (no breakdown), Model, Name, Level, Type, Environment**. Time buckets are chosen automatically from the time range ([events-table-charts](https://langfuse.com/docs/observability/features/events-table-charts)). The chart cannot apply numeric-measure filters, scores/metadata/comments filters, full-text search, or presence checks (`has:`/`-has:`) — these are shown dimmed/struck-through rather than dropped ([events-table-charts](https://langfuse.com/docs/observability/features/events-table-charts)).

**Curated dashboards:** Latency, Cost, and Usage; the **Langfuse Usage Management** dashboard exposes Total Trace Count, Total Observation Count, Total Score Count (numeric + categorical) widgets used to compute billable units ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards), [billable-units](https://langfuse.com/docs/administration/billable-units)). The project **Home** page is itself a dashboard built from regular widgets; any dashboard can be set as the project Home ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards)).

**Widget governance:** ⋯ menu supports Copy to clipboard, Paste to the right, Duplicate, **Download as JSON**, **Download data as CSV** (current query result). Widgets export as `{"$langfuseWidget": true, "version": 1, ...}`, dashboards as `{"$langfuseDashboard": true, "version": 1, ...}` with widget config inlined and no DB IDs — portable across projects and instances; import by dragging the JSON onto a dashboard. A widget's own environment filter overrides the dashboard environment selector for that widget only ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards)).

**Programmatic dashboard management:** Public API endpoints under `/api/public/unstable` cover dashboards, placements, and widgets — `/api/public/unstable/dashboards`, `/api/public/unstable/dashboards/{dashboardId}`, `.../placements`, `.../placements/{placementId}`, `/api/public/unstable/dashboard-widgets`, `/api/public/unstable/dashboard-widgets/{widgetId}` — and are explicitly flagged **unstable** ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards), [openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)). The Langfuse CLI and MCP server expose the same operations ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards)).

### 2c. Score analytics (built-in)

Single-score view: statistics card (total count, mean/mode, standard deviation), Distribution chart, Trend Over Time chart. Two-score comparison adds: matched count, Pearson & Spearman correlation, MAE & RMSE (numeric), Cohen's Kappa / F1 / Overall Agreement (categorical & boolean), plus a Score Comparison Heatmap ([score-analytics](https://langfuse.com/docs/evaluation/scores/score-analytics)). Text scores are **not** supported in Score Analytics ([score-analytics](https://langfuse.com/docs/evaluation/scores/score-analytics)).

### 2d. Alerts on metrics

Data source ∈ {Observations, Scores (numeric), Scores (categorical), Scores (boolean)}; Metric = aggregation + measure ("`avg latency`, `count`, `p95 cost`"); Filters by model name, tags, user ID, environment, Boolean value. Operators `>`, `≥`, `<`, `≤`, `=`, `≠`; required alert threshold, optional warning threshold, and a Window (e.g. 1 hour, 1 day, 1 week). No-data modes: treat as 0 (default) / keep previous severity / show `NO_DATA` / notify after sustained `NO_DATA`. Renotify off by default, or every N minutes (1–10,080). Severities: `UNKNOWN`, `OK`, `WARNING`, `ALERT`, `NO_DATA`, `PAUSED`. Channels: Slack, HMAC-signed Webhook, GitHub Actions `workflow_dispatch` ([alerts](https://langfuse.com/docs/observability/features/alerts)). Cloud limits: 2/20/50/100 alerts on Hobby/Core/Pro/Enterprise; self-hosted v4 has no alert limit ([alerts](https://langfuse.com/docs/observability/features/alerts), [pricing](https://langfuse.com/pricing)). Metrics API v2 rate limits: 100/day (Hobby), 100/hour (Core), 500/hour (Pro), custom (Enterprise) ([pricing](https://langfuse.com/pricing)).

## 3. Cost tracking

**How cost is computed.** For every LLM generation Langfuse records **usage details** (units per usage type, e.g. `input`, `output`, `cached_tokens`, `audio_tokens`) and **cost details** (USD per usage type), captured on observations of type `generation` and `embedding`. Each is either **ingested** (sent from the LLM response) or **inferred** (from the `model` parameter via a model definition storing prices per usage type). "When both are available, **ingested values take priority** over inferred ones" ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)).

**Model definitions / `models` table.** Managed in **Project Settings > Models**; a definition holds a `match_pattern` (regex, e.g. `(?i)^(gpt-4-0125-preview)$`), prices per usage type, and a tokenizer. "User-defined models take priority over models maintained by Langfuse." Managed programmatically via `GET /api/public/models`, `POST /api/public/models`, `GET /api/public/models/{id}`, `DELETE /api/public/models/{id}` ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)). Langfuse ships predefined models for OpenAI, Anthropic and Google; default prices are maintained in the OSS repo and audited daily by an automated workflow against official provider sources ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)).

**Tokenizers supported:** `gpt-4o` → `o200k_base` (tiktoken); `gpt*` → `cl100k_base`; `claude*` → `@anthropic-ai/tokenizer`, with the explicit caveat "their tokenizer is not accurate for Claude 3 models" ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)).

**Pricing tiers.** A model can have multiple tiers, each with Name, Priority (0 reserved for default), Conditions, and Prices per usage type. Conditions draw on usage details (regex match on keys, sum values, compare with `gt`/`gte`/`lt`/`lte`/`eq`/`neq`), model parameters (top-level key vs exact values), or metadata. All conditions in a tier must match; tiers evaluate in priority order and fall back to the default tier. Documented examples: Claude Sonnet 4.5 "Large Context" tier with `input > 200000`; OpenAI Fast mode matching top-level `service_tier` ∈ {`fast`, `priority`} ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)).

**Ingesting cost directly:** supported and recommended for custom/self-hosted models, private pricing, or exact provider counts. `generation.update(usage_details={"input":..., "output":..., "cache_read_input_tokens":...}, cost_details={"input": 1, "cache_read_input_tokens": 0.5, "output": 1})`; `total` is derived as the sum of usage types if not set ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)). Cost is calculated **at ingestion time**, so updated default prices "apply only to new generations" ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)).

**Known limitation:** cost inference by tokenizing input/output is not supported for reasoning models such as OpenAI o1 — without ingested token counts Langfuse cannot infer cost, because reasoning tokens are billed as output but are invisible to Langfuse ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)).

**Cost as a first-class dashboard metric:** yes — `totalCost` / `inputCost` / `outputCost` are Metrics API measures with `sum`/`avg`/`p50`/`p95`/`p99`/`histogram` aggregations ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)); Cost is a first-class metric in the chart builder ([events-table-charts](https://langfuse.com/docs/observability/features/events-table-charts)); a curated **Cost Dashboard** exists; and cost is a documented alert dimension ("p95 cost") ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards), [alerts](https://langfuse.com/docs/observability/features/alerts)). The documented cost dashboard shows "cost by model, cost over time, and top users and use cases by cost" ([token-and-cost-tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)). Separately, **spend alerts** monitor your Langfuse Cloud *bill* (not LLM costs), checked every 60–90 minutes, emailed to Owner/Admin, firing at most once per billing cycle per alert ([spend-alerts](https://langfuse.com/docs/administration/spend-alerts)).

## 4. Evaluations

**Scores data model.** `Score` has `id`, `name`, `value` (number), `stringValue`, `dataType` ∈ {`NUMERIC`, `CATEGORICAL`, `BOOLEAN`, `TEXT`}, `source` ∈ {`API`, `EVAL`, `ANNOTATION`}, `comment`, `configId`. "Each Score references **exactly one** of `Trace`, `Observation`, `Session`, or `DatasetRun`" ([scores/data-model](https://langfuse.com/docs/evaluation/scores/data-model)). `ScoreConfig` enforces a schema: data type, min/max (numeric), custom categories (categorical), 1–500 characters (text); configs are **immutable but can be archived** ([scores/data-model](https://langfuse.com/docs/evaluation/scores/data-model)).

**LLM-as-a-judge.** Judge prompt with `{{variables}}` mapped to observation input/output/metadata/tool calls (plus Expected Output and Experiment Item Metadata for experiments); model selectable per evaluator or project default; score type Numeric/Categorical/Boolean (categorical may allow multiple matches). Targets are **Observations** (recommended for production) or **Experiments**; **trace-level evaluators are deprecated** — on Cloud they keep running until the v4 cutover on **2026-11-16**, after which they stop producing results; on self-hosted v4 in `events_only` mode they also stop ([llm-as-a-judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)). Observation-level evaluators "do not load sibling or child observations from the same trace" and should target a logical root observation when whole-request context is needed ([llm-as-a-judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)). **Where they run:** "executed by the Langfuse **worker**" — renders the prompt, calls the model through the project's LLM connection, writes the score back; "there is no option to run managed evaluators outside the worker". Self-hosters must give the worker (not web) egress to the LLM provider; execution can be pinned with `QUEUE_CONSUMER_EVAL_EXECUTION_QUEUE_IS_ENABLED` and scaled with `LANGFUSE_EVAL_EXECUTION_WORKER_CONCURRENCY` (default `5`) ([llm-as-a-judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)). Multimodal evaluation of images/audio/documents is supported; self-hosters configure `LANGFUSE_EVALUATOR_MEDIA_*` ([llm-as-a-judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)).

**Code evaluators.** A Python or TypeScript `evaluate` function run inside Langfuse, returning one or more scores; for deterministic checks (JSON validity, required fields, keyword rules). They require observations ingested with an OTEL-based SDK (Python SDK v3+, JS/TS SDK v4+), use a **separate worker queue and sandbox**, and on self-hosted deployments "are disabled when no dispatcher is set" ([code-evaluators](https://langfuse.com/docs/evaluation/evaluation-methods/code-evaluators)). A third experimental judge type, **Jev as a judge** (TypeSafe decision model), is available ([online get-started](https://langfuse.com/docs/evaluation/get-started/online)).

**Rules (online evaluation).** An evaluator defines *how* to score; a **rule** defines *which* incoming observations are scored: filters + sampling rate + one or more evaluators. The UI shows matching volume for the past 7 days and an estimated LLM-as-judge cost so the sampling rate can be lowered. Evaluators can also be run on selected historical observations via **batch evaluation** ([get-started/online](https://langfuse.com/docs/evaluation/get-started/online)).

**Annotation queues (human review).** Queues require a `ScoreConfig` defining the scoring dimensions; traces, observations **or sessions** can be added via bulk selection or the `Annotate` dropdown on a single item; reviewers fill the score dimensions and click "Complete + next". Queues can also be used to hand experiment results to a QA team ([annotation-queues](https://langfuse.com/docs/evaluation/evaluation-methods/annotation-queues)). Cloud queue limits: 1 (Hobby), 3 (Core), unlimited (Pro/Enterprise) ([pricing](https://langfuse.com/pricing)).

**Datasets & experiments.** Datasets hold structured test cases; experiments run via UI, SDK, or OpenTelemetry, with side-by-side comparison against a baseline and regression inspection ([datasets](https://langfuse.com/docs/evaluation/experiments/datasets), [compare-experiments](https://langfuse.com/docs/evaluation/experiments/compare-experiments)). CI gating uses the `langfuse/experiment-action` GitHub Action on `pull_request`, raising `RegressionError` when a score violates a threshold; works on Cloud and self-hosted ([evaluation overview](https://langfuse.com/docs/evaluation/overview)).

**Are scores chartable / dashboardable / filterable?** Yes on all three: score views in the Metrics API with 15 dimensions and `count`/`value` measures ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)); score data as a widget data source including numeric/categorical/boolean ([custom-dashboards](https://langfuse.com/docs/metrics/features/custom-dashboards)); score filters in the search bar (`scores.*` matches regardless of level) ([filter-search-bar](https://langfuse.com/docs/observability/features/filter-search-bar)); and Score Analytics for distribution/correlation ([score-analytics](https://langfuse.com/docs/evaluation/scores/score-analytics)). Note: billable units count scores — "`Units` = `Count of Traces` + `Count of Observations` + `Count of Scores`", including scores created by Langfuse features such as LLM-as-a-Judge, Annotation Queues, and experiments ([billable-units](https://langfuse.com/docs/administration/billable-units)).

## 5. Time range, filter, group-by

| Capability | Langfuse |
|---|---|
| Time granularity | `auto`, `minute`, `hour`, `day`, `week`, `month` ([openapi.yml](https://cloud.langfuse.com/generated/api/openapi.yml)) |

## 7. Prometheus / OTEL

**OTLP ingestion — supported.** Langfuse receives traces on `/api/public/otel` (OTLP). Health/readiness check endpoints exist as a separate feature ([health-readiness-endpoints](https://langfuse.com/self-hosting/configuration/health-readiness-endpoints)). → treat Prometheus scraping as **[UNVERIFIED / not documented]**.

**License and gating.** "Langfuse is open source and can be self-hosted using Docker on your own infrastructure. Some add-on features require a [license key]." Enterprise deployments "use limited telemetry for license compliance"; removing the env var and restarting disables EE features while core OSS features keep working ([license-key](https://langfuse.com/self-hosting/license-key)).

**Architecture.** Same codebase as Cloud; two application containers (Langfuse Web, Langfuse Worker) plus Postgres (OLTP), ClickHouse (OLAP — traces/observations/scores), Redis/Valkey (cache + queue) and S3/blob storage (raw events, multi-modal attachments, exports); LLM API/gateway optional. Traces are received in batches by Web, written to S3 immediately, queued via Redis, then ingested into ClickHouse by Worker; all events are persisted to S3 before DB writes for recoverability. "Langfuse processes **90B+ observations per month**", "trusted by **21 of the Fortune 50**", Docker images pulled "38M+ times" ([self-hosting](https://langfuse.com/self-hosting)).

**Docker Compose.** Clone the repo, set secrets in `docker-compose.yml`, `docker compose up`, UI at `http://localhost:3000`. Terraform modules for AWS, Azure, GCP; community templates for Render and Railway ([self-hosting](https://langfuse.com/self-hosting)).

**SSO.** Cloud: email/password, Google/GitHub/Microsoft/ClickHouse Cloud, plus **Enterprise SSO via OIDC** (Okta, Authentik, OneLogin, Azure AD, Keycloak, WorkOS, JumpCloud) — "Langfuse supports authentication via **OIDC only. ## 9. Retention

**Cloud data access windows:** Hobby 30 days, Core 90 days, Pro 3 years, Enterprise 3 years ([pricing](https://langfuse.com/pricing)). **Data retention management** (automatic deletion) is Pro, Enterprise, and self-hosted **EE**; Hobby and Core are "Not Available" ([data-retention](https://langfuse.com/docs/administration/data-retention)).

**Configuration.** Per-project, in **Project Settings → Data Retention**, minimum **3 days**; settable via the Organization Management API; on self-hosted, `LANGFUSE_INIT_PROJECT_RETENTION` sets the retention of the project created at startup. "Retention is a per-project setting. There is no organization- or team-level retention policy" ([data-retention](https://langfuse.com/docs/administration/data-retention)).

**Behavior.** Nightly selection and deletion of traces/observations/scores/media older than the window, keyed on: Traces → `timestamp`; Observations → `start_time`; Scores → `timestamp`; Media Assets → `created_at`. Deleted assets cannot be recovered; the docs recommend a Blob Storage Export to preserve data beyond the window ([data-retention](https://langfuse.com/docs/administration/data-retention)).

**Scope table:** Traces/observations/scores deleted even when linked to datasets or experiments; **audit logs unaffected**; **datasets and dataset items unaffected**; dataset runs and run items remain but their linked traces/observations/scores can expire; media stored in Langfuse deleted unless associated with saved dataset items. Adding a trace to a dataset does not protect the trace or reset its retention window ([data-retention](https://langfuse.com/docs/administration/data-retention)).

**Defaults.** "Without a retention policy, Langfuse does not automatically delete event data… On self-hosted instances, data is stored indefinitely by default." Self-hosted retention additionally requires `s3:DeleteObject` on all buckets, and on versioned buckets delete markers / non-current versions must be removed manually or via a lifecycle rule ([data-retention](https://langfuse.com/docs/administration/data-retention)).

**API read window.** On Cloud, the Observations API v2 read window is 30 days on Hobby and 90 days on Core, which bounds what a read-driven deletion workflow can discover ([data-deletion](https://langfuse.com/docs/administration/data-deletion)).

**Manual deletion.** Single trace, batch of traces, all traces in a session (via API, iterating `GET /api/public/v2/observations` with `sessionId` in month windows and `DELETE /api/public/traces` in batches of 1,000 trace IDs), or all traces matching a filter query. Trace deletions cascade to related scores and observations across all data storages ([data-deletion](https://langfuse.com/docs/administration/data-deletion)).

## 1. Trace-level observability

**Data model.** "Every unit of work an agent performs… is recorded as a **run**"; runs for a single operation are collected into a **trace** (bound by a unique trace ID); traces from multi-turn sessions are linked as a **thread**; a **trajectory** is a "flat, ordered list of messages" projection over the traces in a thread, deduplicated and with nesting removed. "If you are familiar with OpenTelemetry, you can think of a run as a span." A **project** is a container for all traces of one application ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)).

| | Trace | Thread | Trajectory |
|---|---|---|---|
| Shape | Tree of runs | Sequence of traces | Flat, ordered list of messages |
| Contains | Every run, with full inputs and outputs | Every run in every linked trace | Every message in every linked trace, deduplicated ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)) |

**Nesting depth cap — hard limit:** "Each trace is limited to a maximum of **25,000 runs**. Once the trace reaches this limit, LangSmith will reject any additional runs that you send for that trace." ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)).

**Run types (7):** `chain`, `llm`, `embedding`, `prompt`, `tool`, `retriever`, `parser` ([run-data-format](https://docs.langchain.com/langsmith/run-data-format)).

**Threads / sessions.** Group traces by passing a `metadata` key named `session_id` **or** `thread_id` with a unique value ([threads](https://docs.langchain.com/langsmith/threads)). Critical caveat: "To ensure filtering and token counting work correctly across your entire thread, you must set the thread metadata (`session_id` or `thread_id`) on **all runs**, including child runs within a trace" — otherwise those runs are excluded from thread filtering and token/cost aggregation ([threads](https://docs.langchain.com/langsmith/threads), [cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)). A thread is a sequence of **turns**, each turn being one trace ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)). Thread views: Messages, Turns, Details, plus Trajectory ([threads](https://docs.langchain.com/langsmith/threads)).

**User tracking.** `ls_user_id` is a filterable Field = "The LangSmith user the run is attributed to" ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)). There is no separate end-user tracking dimension beyond metadata/`ls_user_id` in the traced vocabulary ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)).

**Tags.** "Strings you can attach to runs to categorize, filter, and group them in the LangSmith UI" ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)).

**Metadata.** "A collection of key-value pairs you can attach to runs. For example, application version, environment, or any other contextual information… you can use metadata to filter and group runs" ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)). **Metadata and tags are not propagated** between parent and child runs in either direction ([dashboards](https://docs.langchain.com/langsmith/dashboards)). Model attribution uses the reserved keys `ls_provider` and `ls_model_name` ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)).

**Release / version tracking.** No first-class `release`/`version` field. Version tracking is done by convention through metadata keys (docs use `metadata.ls_model_name` as the group-by example) — a functional gap versus Langfuse's first-class `release` and per-observation `version` ([dashboards](https://docs.langchain.com/langsmith/dashboards)).

**Search / filter (UI).** Two filtering experiences exist depending on the project; the newer one is "a single search bar with a scope selector to its left". A query is clauses of `field:operator value`, combined with `AND`, and a **scope selector** chooses what each clause matches: **Any run**, **Root run**, or **Thread**. Additional rows combine with `AND`; each scope holds at most one row, so **Threads** and **Runs** selections accept three rows and **Traces** accepts two ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)).

**Filter operators:** `is` (`field:value`), `is not` (`-field:value`), `matches` (`field:~value`, full-text, quote for phrase), `does not match`, `wildcard` (`field:value*`), `exists` (`field:*`), `does not exist` (`-field:*`), `comparison` (`field:>value`, also `>=`, `<`, `<=`), `inclusive range` (`field:[10 TO 20]`), `exclusive range` (`field:{10 TO 20}`), `mixed range` (`field:[10 TO 20}`). Full-text fields (`input`, `output`, `metadata`, `error`) accept `~` only; comparison/range applies to numeric and timestamp fields. Multi-value matching requires `OR` — "Listing several values inside one clause is not supported." ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)).

**Filterable fields — Run scope** ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)):

| Group | Fields |
|---|---|
| Run attributes | `name` (wildcards), `status` (`pending`/`success`/`error`/`interrupted`), `run_type`, `tags` |
| Content | `input`, `output`, `metadata`, `error`, `attachments` (dot notation for JSON keys) |
| Identity | `id`, `trace_id`, `thread_id`, `parent_run_id`, `ls_user_id` |
| Performance | `latency`, `first_token_time`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `prompt_cost`, `completion_cost`, `total_cost`, `prompt_token_details`, `completion_token_details`, `prompt_cost_details`, `completion_cost_details` (component access e.g. `prompt_token_details.cache_read`, `completion_token_details.reasoning`) |
| Feedback | `feedback.<key>.<subfield>` where subfield ∈ `key`, `score`, `value`, `comment`, `source`, `error`; `feedback:*` for any feedback ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)) |

**Filterable fields — Thread scope:** `thread_id`, `turn_count`, `num_errored_turns`, `thread_duration` (first turn start → last turn end), `trace_latency_p50`, `trace_latency_p99`, `total_tokens`, `total_cost`, plus the four token/cost detail breakdowns. Run fields such as `name`, `status`, `input` are **not** available in Thread scope ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)).

**Saved views.** "Saved views store a filter for reuse. A view belongs to the tracing project rather than to the person who created it, so anyone with access to the project can select it." Each entry lists the scopes its filter uses ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)). Thread-level filters can also be saved on the Threads tab and "look through all runs and surface a thread if at least 1 run matches" ([threads](https://docs.langchain.com/langsmith/threads)).

**Programmatic filter language (SDK/REST, distinct from the UI syntax).** Filter arguments: `project_id`/`project_name`, `run_ids`, `filter`, `trace_filter` (root run of the trace), `tree_filter` (any run in the tree), `select` (field projection), and an experimental natural-language `query`. Comparators: `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `has`, `search`; logical `and`/`or`; examples `eq(status, "error")`, `gte(latency, 1.5)`, `has(tags, "production")`, `search("invoice")`, `and(in(metadata_key, ["session_id","thread_id"]), eq(metadata_value, "<id>"))`, `and(eq(feedback_key, "correctness"), lt(feedback_score, 0.5))`. Performance tip: passing `select` and excluding `inputs`/`outputs` "can significantly improve query performance and reduce response sizes" ([trace-query-syntax](https://docs.langchain.com/langsmith/trace-query-syntax)).

**Other trace features fetched:** distributed tracing ([distributed-tracing](https://docs.langchain.com/langsmith/distributed-tracing)); inline annotation ([annotate-traces-inline](https://docs.langchain.com/langsmith/annotate-traces-inline)); manage a trace incl. delete ([manage-trace](https://docs.langchain.com/langsmith/manage-trace)); multimodal traces and file uploads ([upload-files-with-traces](https://docs.langchain.com/langsmith/upload-files-with-traces)); Insights automatic pattern/failure-mode detection ([insights](https://docs.langchain.com/langsmith/insights)); Engine for recurring issue detection ([observability](https://docs.langchain.com/langsmith/observability)).

## 3. Cost tracking

**Two methods:** automatically from token counts + model prices for LLM calls, or manually specified on any run including non-LLM types ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)).

| Method | LLM runs | Other runs |
|---|---|---|
| Automatically | LangChain; `@traceable` with OpenAI/Anthropic/OpenAI-compatible; LangSmith OpenAI/Anthropic wrappers; documented manual token/cost path for other providers | Not applicable |
| Manually | Non-linear/custom cost functions | Any run type, e.g. tool calls, retrieval ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)) |

**Automatic cost prerequisites:** token counts, the model and provider, and the model price. Token counts are supplied either by setting a `usage_metadata` field on the run's metadata (via `run.set(usage_metadata=...)` / `runTree.metadata.usage_metadata = ...`) or by returning a `usage_metadata` key in the traced function's output — "LangSmith will extract it from the output" ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)).

**Documented usage_metadata fields (partial, from examples):** `input_tokens`, `output_tokens`, `total_tokens`, `input_token_details: {"cache_read": N}`, plus `input_cost`, `input_cost_details`, `output_cost`, `total_cost` ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)). Cost can be sent for non-LLM runs via `usage_metadata={"total_cost": 0.0015}` on a tool run ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)). Provider/model attribution uses `ls_provider` and `ls_model_name` metadata ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)).

**Cost presentation in the UI.** Three categories: **Input** (cache reads, text tokens, image tokens), **Output** (reasoning tokens, text tokens, image tokens), **Other** ("Costs from tool calls, retrieval steps, or any custom runs"). Visible in the trace tree (total for the trace, aggregated per parent run, breakdowns per child run), in project stats, and in dashboards ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)).

**Custom model prices.** A **model price map** exists as a first-class API resource: `GET /api/v1/model-price-map`, plus create/update/delete endpoints ([model-price-map](https://docs.langchain.com/langsmith/smith-api/model-price-map/read-model-price-map)). Evaluator spend tracking and limits "use the per-model pricing configured under Model pricing" ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)).

**Non-linear pricing.** Gemini 2.5 Pro Preview and Gemini 2.5 Pro "use a stepwise cost function, which LangSmith supports by default. For any other model with non-linear pricing, calculate costs client-side and send them as `usage_metadata`" ([cost-tracking](https://docs.langchain.com/langsmith/cost-tracking)).

**Cost as a first-class dashboard metric:** yes — Cost is a custom-chart metric with Total/Input/Output variants, and `total_cost`, `prompt_cost`, `completion_cost`, `cost_p50`, `cost_p99` are API metrics; Cost & Tokens is a dedicated prebuilt section; global group-by splits cost by tag/metadata ([dashboards](https://docs.langchain.com/langsmith/dashboards), [create-chart](https://docs.langchain.com/langsmith/smith-api/charts/create-chart)).

**Evaluator spend controls.** Per-evaluator weekly spend cap; org-wide default with per-evaluator override; "When weekly spend reaches the effective limit, LangSmith pauses the evaluator on that project or dataset until the limit resets at Monday 12AM UTC or the limit is manually increased" ([online-evaluations-llm-as-judge](https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge)). The Evaluators table shows Evaluator Trace Count (this week), Spend (this week), and Spend Status (Under limits / Unlimited / limit hit) when spend tracking is enabled ([evaluators](https://docs.langchain.com/langsmith/evaluators)).

## 4. Evaluations

**Feedback / scoring primitives.** "Feedback allows you to score an individual run based on certain criteria. Each feedback entry consists of a tag and a score, and is bound to a run by a unique run ID. Feedback can be continuous or discrete (categorical)" ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)). By convention, evaluator results must be returned as a numerical metric (`int`/`float`/`bool`, or `{"key": ..., "score": ...}`) or a categorical metric (`str`, or `{"key": ..., "value": ...}`) ([metric-type](https://docs.langchain.com/langsmith/metric-type)). Multiple scores per evaluator are supported ([multiple-scores](https://docs.langchain.com/langsmith/multiple-scores)).

**Evaluators are workspace-level resources** — "You can attach a single evaluator to multiple tracing projects and datasets, so you can apply consistent evaluation logic across your work without recreating it each time." Configuration (sampling rate, filters, spend limits) is set **per attachment**, not per evaluator ([evaluators](https://docs.langchain.com/langsmith/evaluators), [evaluation-concepts](https://docs.langchain.com/langsmith/evaluation-concepts)).

**Evaluator types:** **LLM as a judge**, **Code**, **Composite score evaluators** (scoped to individual projects/datasets and not listed in the workspace Evaluators table), plus **LangChain tuned evaluators** and templates ([evaluators](https://docs.langchain.com/langsmith/evaluators)).

**Online (production) evaluation.** Run-level LLM-as-a-judge evaluators score a single run; multi-turn evaluators score whole threads ([online-evaluations-llm-as-judge](https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge)). Configuration: a **filter** on which runs trigger ("Evaluators use the filter builder, with the same fields and operators described in Filter traces (ClickHouse)"), a **sampling rate** ("to control costs, you may want to set a filter to only apply the evaluator to 10% of traces. In order to do this, you would set the sampling rate to 0.1"), an optional **backfill** ("Apply to past runs from date" / "Apply to past threads from date" — "You can only backfill when you create the rule", processed as a background job), and a **spend limit** ([online-evaluations-llm-as-judge](https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge)). Retention side effect: "When an online evaluator runs on any run within a trace, the trace will be auto-upgraded to extended data retention" — with an opt-out when the project default is the base tier ([online-evaluations-llm-as-judge](https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge), [usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)).

**Human review / annotation queues.** Two queue styles ([annotation-queues](https://docs.langchain.com/langsmith/annotation-queues)):
- **Single-run annotation queues** — one item at a time, either a **run item** or a **thread item**; reviewers submit any configured rubric feedback; run items additionally support **assertions** for offline evaluation. A queue can mix run and thread items.
- **Pairwise annotation queues (PAQs)** — two runs side-by-side; reviewer picks which is better or equivalent against the rubric.

Queue settings: rubric feedback keys with descriptions, optional default dataset (run items only; thread items do not support default datasets), reviewer count or reservation length, "All workspace members review each run", "Enable reservations on runs", "Number of reviewers per run" (reviewers cannot see each other's feedback) ([annotation-queues](https://docs.langchain.com/langsmith/annotation-queues)). Queues and feedback configs are manageable via the SDK ([annotation-queues-sdk](https://docs.langchain.com/langsmith/annotation-queues-sdk)).

**Datasets & experiments (offline).** A dataset is "a collection of examples"; an example is a test input + reference output pair, with optional metadata "used to create filtered views of a dataset". An **experiment** "represents the results of evaluating a specific application version on a dataset. Each experiment captures outputs, evaluator scores, and execution traces for every example." LangSmith displays all experiments on a dataset and supports side-by-side comparison ([evaluation-concepts](https://docs.langchain.com/langsmith/evaluation-concepts)). Related: [manage-datasets](https://docs.langchain.com/langsmith/manage-datasets), [analyze-an-experiment](https://docs.langchain.com/langsmith/analyze-an-experiment), [compare-experiment-results](https://docs.langchain.com/langsmith/compare-experiment-results), [filter-experiments-ui](https://docs.langchain.com/langsmith/filter-experiments-ui), [evaluate-on-intermediate-steps](https://docs.langchain.com/langsmith/evaluate-on-intermediate-steps).

**Where evaluators run:** the [Evaluators](https://docs.langchain.com/langsmith/evaluators) page, or [Rules](https://docs.langchain.com/langsmith/rules) to run them automatically on projects or datasets; additionally via the SDK ([evaluate-llm-application](https://docs.langchain.com/langsmith/evaluate-llm-application)), pytest ([pytest](https://docs.langchain.com/langsmith/pytest)), OpenTelemetry ([evaluate-with-opentelemetry](https://docs.langchain.com/langsmith/evaluate-with-opentelemetry)), and CI/CD ([cicd-pipeline-example](https://docs.langchain.com/langsmith/cicd-pipeline-example)) ([evaluation-concepts](https://docs.langchain.com/langsmith/evaluation-concepts)).

**Are eval scores chartable?** Yes — **Feedback score** is a first-class custom-chart metric (Average / Minimum / Maximum over a selected feedback key) ([dashboards](https://docs.langchain.com/langsmith/dashboards)); Feedback Scores is a prebuilt section (average for numeric, category counts for categorical) ([dashboards](https://docs.langchain.com/langsmith/dashboards)); **Feedback Label** is a group-by attribute ([dashboards](https://docs.langchain.com/langsmith/dashboards)); `feedback`, `feedback_score_avg`, `feedback_values`, `feedback_stats`, `thread_feedback_stats`, `session_feedback_stats` are API metrics ([create-chart](https://docs.langchain.com/langsmith/smith-api/charts/create-chart), [stats-runs](https://docs.langchain.com/langsmith/smith-api/run/stats-runs)); feedback is a filterable field with `score`, `value`, `comment`, `source`, `error` subfields ([filter-traces](https://docs.langchain.com/langsmith/filter-traces)); Feedback Score is an alert metric ([alerts](https://docs.langchain.com/langsmith/alerts)); and evaluator score auditing is supported ([audit-evaluator-scores](https://docs.langchain.com/langsmith/audit-evaluator-scores)).

**Insights (AI analysis, gated).** "Insights automatically analyzes your traces to detect usage patterns, common agent behaviors, and failure modes" using hierarchical categorization; reports can take up to 30 minutes. **Available for LangSmith Plus and Enterprise plans** ([insights](https://docs.langchain.com/langsmith/insights)).

## 6. Exports and APIs

**Base and auth.** `https://api.smith.langchain.com`; authenticate with the `X-Api-Key` header; some org-scoped calls also accept bearer tokens plus `x-tenant-id`/`x-organization-id` ([model-price-map](https://docs.langchain.com/langsmith/smith-api/model-price-map/read-model-price-map), [stats-runs](https://docs.langchain.com/langsmith/smith-api/run/stats-runs)).

**Analytics / aggregate endpoints** ([stats-runs](https://docs.langchain.com/langsmith/smith-api/run/stats-runs), [group-runs](https://docs.langchain.com/langsmith/smith-api/run/group-runs), [stats-group-runs](https://docs.langchain.com/langsmith/smith-api/run/stats-group-runs), [query-runs](https://docs.langchain.com/langsmith/smith-api/run/query-runs)):

| Endpoint | Purpose |
|---|---|
| `POST /api/v1/runs/query` | Query runs (with `filter`, `trace_filter`, `tree_filter`, `search_filter`, `select`, time range, `group_by`, `groups`) |
| `POST /api/v1/runs/stats` | "Get all runs by query in body payload" — returns stats per `RunStatsSelect` metric, supports `group_by` (`RunStatsGroupBy`), `groups`, `max_groups` |
| `POST /api/v1/runs/group` | Group runs (`RunGroupRequest`: `group_by`, `filter`, `start_time`, `end_time`) |
| `POST /api/v1/runs/group/stats` | "Get stats for the grouped runs" |

**Dashboard / chart endpoints:** `POST /api/v1/charts/create` and the chart/section CRUD family (`create-chart`, `read-charts`, `read-single-chart`, `read-chart-preview`, `update-chart`, `delete-chart`, `create-section`, `clone-section`, `read-sections`, `update-section`, `delete-section`, plus `org-*` organization-scoped variants listed under `smith-api/charts/*`) ([create-chart](https://docs.langchain.com/langsmith/smith-api/charts/create-chart), [paths index](https://docs.langchain.com/langsmith/api-ref-control-plane)). `GET` dashboard data via `smith-api/orgs/get-dashboard` and the tracing-project prebuilt dashboard via `smith-api/tracer-sessions/get-tracing-project-prebuilt-dashboard` ([paths index](https://docs.langchain.com/langsmith/api-ref-control-plane)).

**Model price map CRUD:** `GET /api/v1/model-price-map`, plus create/update/delete ([model-price-map](https://docs.langchain.com/langsmith/smith-api/model-price-map/read-model-price-map)).

**Bulk export to object storage.** "Export LangSmith trace data to an S3-compatible bucket in **Parquet** format, matching the fields in the Run data format." Destinations are **S3 or any S3-compatible bucket (such as GCS or MinIO)** — `POST /api/v1/bulk-exports/destinations` with bucket, prefix, region or endpoint URL, and static keys or other credential formats; credentials stored encrypted and validated on save. Export jobs via `POST /api/v1/bulk-exports` with destination id, project/`session_id` or `all_experiments`, time range, **field filtering**, and **filter expressions**; compression defaults to `zstandard` (Snappy shown for BigQuery); `format_version: v2_beta` produces UTC timezone-aware timestamps for BigQuery. Output paths are Hive-partitioned by `export_id`, `tenant_id`, `session_id`, `resource`, `year`, `month`, `day`, queryable in BigQuery ([data-export](https://docs.langchain.com/langsmith/data-export), [data-export-destinations](https://docs.langchain.com/langsmith/data-export-destinations), [big-query-bulk-export](https://docs.langchain.com/langsmith/big-query-bulk-export)). **Scheduling:** include `interval_hours` and omit `end_time`; spawned exports carry `source_bulk_export_id`; cancelling the source does **not** cancel already-spawned exports. Bulk exports have a **72-hour runtime timeout** with automatic retry ([data-export](https://docs.langchain.com/langsmith/data-export), [data-export-monitor](https://docs.langchain.com/langsmith/data-export-monitor)). Cloud quotas: **250 bulk-export creations per hour per workspace**, **200 active scheduled exports per workspace** (429 past that). **Plan gating:** "For customers who signed up after August 3, 2026, bulk export is only available on the LangSmith **Enterprise** plan. Customers who signed up on or before August 3, 2026, can use bulk export on Plus or Enterprise plans until February 1, 2027." ([data-export](https://docs.langchain.com/langsmith/data-export), [big-query-bulk-export](https://docs.langchain.com/langsmith/big-query-bulk-export)).

**Granular billable usage API.** One endpoint, two domains via `kind`: `kind=traces` (default, trace count ingested) and `kind=langsmith_deployments` (nodes executed, agent runs, agent uptime). Broken down by **workspace, project, user, or API key**; same time-bucketed shape for both kinds; requires `organization:read`. CSV export exists (`smith-api/orgs/export-granular-usage-csv`). Cloud trace data collection started **January 5, 2026**; self-hosted requires `DEFAULT_ORG_FEATURE_ENABLE_GRANULAR_USAGE_REPORTING=true` and `GRANULAR_USAGE_TABLE_ENABLED=true`, and from self-hosted 0.16.0 "long-lived trace usage is no longer tracked" ([granular-usage](https://docs.langchain.com/langsmith/granular-usage)).

**Webhooks & automations.** Rules define **item type** (Runs or Threads), **filter**, **sampling rate** (0–100% in the UI, decimal 0–1 as `sampling_rate` in the API), and **action**. Actions: Add to Annotation Queue, Add to Dataset, Trigger Webhooks, and Extend Data Retention. Execution order within one rule: "1. Add to annotation queue. 2. Add to dataset. 3. Trigger webhook." Each rule polls on an independent schedule, so cross-rule ordering is not guaranteed — use filters to create dependencies ([rules](https://docs.langchain.com/langsmith/rules)). Thread rules wait for the conversation to complete (configurable thread idle time); a thread rule's webhook payload has a top-level `threads` array ([rules](https://docs.langchain.com/langsmith/rules), [webhooks](https://docs.langchain.com/langsmith/webhooks)). Retention extension per action is admin-only, gated by the `rules:configure-retention` permission ([rules](https://docs.langchain.com/langsmith/rules)). Prompt webhooks are a separate API family (`smith-api/prompt-webhooks/*`) ([paths index](https://docs.langchain.com/langsmith/api-ref-control-plane)).

**MCP.** **LangSmith Remote MCP** (OAuth-authenticated, hosted): Cloud endpoints `https://api.smith.langchain.com/mcp` (GCP US), `https://eu.api.smith.langchain.com/mcp` (GCP EU), and an APAC equivalent; self-hosted (v0.15+) `https://<your-langsmith-host>/api/mcp`; BYOC `https://<data_plane_url>/api/mcp`. Auth: OAuth 2.1 with Dynamic Client Registration (RFC 7591) for interactive clients, or a LangSmith API key in the `X-Api-Key` header for programmatic clients; OAuth metadata discoverable at `/.well-known/oauth-authorization-server` (RFC 8414) ([langsmith-remote-mcp](https://docs.langchain.com/langsmith/langsmith-remote-mcp)). The older standalone **LangSmith MCP Server** is marked **deprecated** and exposes the same tool surface: conversation history/threads, prompts, **runs and traces** (`fetch_runs` — "Supports filters (`run_type`, `error`, `is_root`), FQL (`filter`, `trace_filter`, `tree_filter`), and ordering", with character-based pagination), datasets and examples, experiments and evaluations, and billing ([langsmith-mcp-server](https://docs.langchain.com/langsmith/langsmith-mcp-server), [langsmith-remote-mcp](https://docs.langchain.com/langsmith/langsmith-remote-mcp)).

**Docs MCP.** The docs pages advertise "Connect these docs to your agent of choice via MCP" at `/use-these-docs` ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)).

**No CSV/JSON export of dashboard aggregates is documented.** Bulk export is Parquet to object storage ([data-export](https://docs.langchain.com/langsmith/data-export)); dataset downloads exist in CSV/JSONL/OpenAI formats via `smith-api/datasets/download-dataset-csv|jsonl|openai|openai-ft` ([paths index](https://docs.langchain.com/langsmith/api-ref-control-plane)); granular usage has a CSV endpoint ([granular-usage](https://docs.langchain.com/langsmith/granular-usage)).

## 7. Prometheus / OTEL

**OTLP ingestion — supported.** LangSmith "receives spans at its OTLP endpoint and displays them as traces". Cloud base `OTEL_EXPORTER_OTLP_ENDPOINT=https://api.smith.langchain.com/otel` with `OTEL_EXPORTER_OTLP_HEADERS="x-api-key=<key>"`; add `Langsmith-Project=<project name>` to route to a project. Explicit path caveat: `OTEL_EXPORTER_OTLP_ENDPOINT` is a **base URL** and OTLP/HTTP exporters append `/v1/traces` themselves — setting the base to `.../otel/v1/traces` results in `/otel/v1/traces/v1/traces` and a `404`; use the per-signal `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (or a collector's `traces_endpoint`) when you need the full path ([trace-with-opentelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry)). **Self-hosted:** replace the host and append `/api/v1`, e.g. `https://ai-company.com/api/v1/otel` ([trace-with-opentelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry)). For LangChain/LangGraph apps set `LANGSMITH_OTEL_ENABLED=true`; non-LangChain apps use `opentelemetry-exporter-otlp` with a `BatchSpanProcessor`. Process-level metadata via standard `OTEL_RESOURCE_ATTRIBUTES` ("ideal for any custom metadata you want to tag your traces with, such as a username, request ID, environment, or deployment version"), plus `OTEL_SERVICE_NAME` ([trace-with-opentelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry)). Trace redaction through an OTel gateway is documented separately ([otel-gateway-trace-redaction](https://docs.langchain.com/langsmith/otel-gateway-trace-redaction)). The protocol (HTTP/protobuf vs HTTP/JSON vs gRPC) is **not stated** for LangSmith's endpoint in the retrieved page → **[UNVERIFIED]**; the page's `grpc:` block is the collector's receiver config, not LangSmith's transport.

**Prometheus — supported, but for infrastructure/runtime metrics, not trace analytics.** Two distinct surfaces:
1. **LangSmith self-hosted services** "expose metrics at an endpoint, in the Prometheus metrics format. The frontend does not currently expose metrics." Exact endpoints: Backend `http://<langsmith_release_name>-backend.<namespace>.svc.cluster.local:1984/metrics`; Platform Backend `...:1986/metrics`; Playground `...:1988/metrics`; Host Backend (Control Plane only) `...:1985/metrics`. "You can use a Prometheus or OpenTelemetry collector to scrape the endpoints, and export metrics to the backend of your choice." ([export-backend](https://docs.langchain.com/langsmith/export-backend)).
2. **Agent Server** (LangSmith Deployment runtime) "emits metrics through an OpenTelemetry (OTel) client. Metrics use the `lg_api_` name prefix by default (override with `METRIC_PREFIX`)." Prometheus scrape at `GET /metrics` with `format=prometheus`; Deployment UI metrics exposed by default, internal metrics only with `EXPOSE_INTERNAL_METRICS_PROMETHEUS=true`; tiers controlled by `METRIC_MAX_EMITTING_TIER`; Datadog OTLP push via `LSD_DD_API_KEY` to `https://{LSD_DD_ENDPOINT}/v1/metrics` (default `otlp.us5.datadoghq.com`); Prometheus and Datadog can run simultaneously ([self-hosted-agent-server-metrics](https://docs.langchain.com/langsmith/self-hosted-agent-server-metrics)).

**No Prometheus metrics for the trace-analytics data model** (run counts, cost, latency, feedback) are documented — those live in the LangSmith API/dashboards, not a scrape endpoint.

## 8. Self-hosting

**Gating — Enterprise-only.** "Self-hosted LangSmith is an add-on to the **Enterprise plan** designed for our largest, most security-conscious customers… [Contact our sales team] if you want to get a license key to trial LangSmith in your environment." ([self-hosted](https://docs.langchain.com/langsmith/self-hosted), [kubernetes](https://docs.langchain.com/langsmith/kubernetes)). There is no MIT/open-source self-host tier and no free self-hosted option documented.

**Deployment model.** **Helm on Kubernetes** — "You'll use Helm to install LangSmith and its dependencies." Tested on **GKE, EKS, AKS**; requires a `kubectl`-accessible cluster with documented minimum node/storage requirements; installs PostgreSQL, Redis, and **ClickHouse** in-cluster by default (external/managed datastores highly recommended); `langsmithLicenseKey` set in values; "LangSmith requires egress to `https://beacon.langchain.com` for license verification and usage reporting. This is required for LangSmith to function properly." A read-only Helm configuration example exists for clusters enforcing non-root/read-only container policies; "LangSmith containers do not require root privileges." Terraform bundles cluster provisioning, secrets wiring, and the Helm release for AWS, Azure, and GCP ([\
kubernetes](https://docs.langchain.com/langsmith/kubernetes), [self-hosted](https://docs.langchain.com/langsmith/self-hosted)). By default the chart deploys the application containers and the data stores ([self-hosted](https://docs.langchain.com/langsmith/self-hosted)). Note: "Insights (AI-powered trace analysis) and Polly (in-workspace chat) are enabled by default in recent chart versions and require encryption keys at installation time" ([kubernetes](https://docs.langchain.com/langsmith/kubernetes)).

**Included services.** Self-hosted LangSmith comprises services including the LangSmith Playground (forwards requests to LLM APIs) and storage services PostgreSQL (primary transactional store — "almost everything besides traces and feedback"), Redis, ClickHouse, and optional-but-recommended blob storage (AWS S3, Azure Blob Storage, GCS) for trace artifacts and feedback attachments ([self-hosted](https://docs.langchain.com/langsmith/self-hosted)).

**Beyond core tracing, two deployment models exist:** Cloud (US/EU data regions, static NAT egress IPs, 25 MB payload cap, Serverless and Dedicated deployment types in three sizes) versus **self-hosted / hybrid / BYOC** — self-hosted deployments can add a **control plane + data plane** to deploy and manage agents from the LangSmith UI, self-hosted-only platform features include custom PostgreSQL (`POSTGRES_URI_CUSTOM`), custom Redis (`REDIS_URI_CUSTOM`), **listeners**, and full resource customization (Cloud exposes fixed deployment sizes; self-hosted sizes CPU/memory/replicas/storage to your infrastructure) ([cloud-platform-features](https://docs.langchain.com/langsmith/cloud-platform-features), [self-hosted-platform-features](https://docs.langchain.com/langsmith/self-hosted-platform-features), [self-hosted](https://docs.langchain.com/langsmith/self-hosted)).

**Enterprise-gated access & compliance features:** workspace-level **RBAC** with custom roles ("RBAC… is an Enterprise feature for managing workspace-level permissions… Other plans default to using the Admin role for all users") — note Organization User/Viewer roles need **Plus or Enterprise** ([rbac](https://docs.langchain.com/langsmith/rbac)); **ABAC** attribute-based access control ("an Enterprise feature for managing fine-grained access control"; currently only `resource_tag_key` is supported as `attribute_name`, configurable through the API and enforced in both API and UI) ([abac](https://docs.langchain.com/langsmith/abac)); **audit logs** ("available on Enterprise plans"; OCSF v1.7.0 API Activity Class UID 6003 format; `GET /api/v1/audit-logs`) ([audit-logs](https://docs.langchain.com/langsmith/audit-logs)); **Insights** (Plus and Enterprise) ([insights](https://docs.langchain.com/langsmith/insights)); **bulk export** (Enterprise for post-2026-08-03 signups) ([data-export](https://docs.langchain.com/langsmith/data-export)). Enterprise also covers SSO & JIT provisioning, user management, data privacy/PII, and cost controls ([enterprise](https://docs.langchain.com/langsmith/enterprise)). LangSmith "holds SOC 2 Type II, HIPAA, and GDPR certifications" ([enterprise](https://docs.langchain.com/langsmith/enterprise)).

**Cloud-only capabilities (not available self-hosted):** native Slack alert notifications ("available on LangSmith Cloud only. For self-hosted deployments, use the webhook Slack recipe") ([alerts](https://docs.langchain.com/langsmith/alerts)); static NAT IP allowlisting; Cloud deployment types ([cloud-platform-features](https://docs.langchain.com/langsmith/cloud-platform-features)).

## 9. Retention

**Two trace retention tiers** ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)):

| | Base | Extended |
|---|---|---|
| Retention Period | **14 days** | **180 days** |
| Price | See pricing page | See pricing page |

Starting **September 14, 2026**, "the maximum long-lived trace retention period for SaaS customers is changing to **180 days**. Enterprise customers can still customize the extended retention period per workspace up to this new maximum. Changes apply to new traces only—existing traces are unaffected." ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)). The SaaS default retention is also stated as "180 days from ingestion" in the concepts page ([observability-concepts](https://docs.langchain.com/langsmith/observability-concepts)).

**After retention ends:** "traces are no longer accessible in the tracing project UI or via the API. All user data associated with the trace (e.g. inputs and outputs) is deleted from our internal systems shortly after. Some metadata associated with each trace may be retained indefinitely for analytics and billing purposes." ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)).

**Auto-upgrades to extended (with cost impact)** — triggered by: **feedback via API/SDK** that explicitly passes `extend_trace_retention=true` (`extendTraceRetention: true` in TS) — note the LangSmith **UI sends feedback and notes without extending retention**; **online evaluators** that score a trace, when their retention setting is enabled (both trace-level and thread-level evaluators can opt out); **automation rules** with retention extension enabled (matching a single run upgrades the entire trace; a Threads-item-type rule upgrades every trace in the matched thread). **Manual annotation-queue adds do not upgrade retention by default.** Experiments create runs at extended retention by default. ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing), [rules](https://docs.langchain.com/langsmith/rules)).

**Retention-independent behavior.** **Monitoring** "will continue to work even after a base tier trace's data retention period ends. It is powered by trace metadata that exists for >30 days, meaning that your monitoring graphs will continue to stay accurate even on `base` tier traces." **Datasets have an indefinite data retention period** — adding a trace's inputs/outputs to a dataset means they are never deleted ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)).

**Billing model.** LangSmith meters two things separately: all traces regardless of tier, and the number of extended-retention traces — because a base trace recorded on June 30 can be upgraded on July 3, landing in a different billing period ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)).

**Self-hosted retention (TTL).** Configured via Helm: `config.ttl.enabled` and `config.ttl.ttl_period_seconds.longlived` / `.shortlived`; the Helm chart "defaults to **14 days** for `shortlived` and **400 days** for `longlived`". Tier precedence, highest first: **1)** trace upgrade from a run rule or other qualifying action (overrides everything), **2)** project tier, **3)** workspace default ("Changing it affects new projects only unless you apply it to all existing projects"), **4)** organization default, **5)** `shortlived` fallback. Period resolution: `longlived` uses the workspace extended retention period set through the UI if present, otherwise the Helm `longlived` value; `shortlived` uses the Helm value. Self-hosted **Enterprise** customers can configure extended retention at the workspace level through the UI with no environment-variable changes ([self-host-ttl](https://docs.langchain.com/langsmith/self-host-ttl)). Separately, self-hosted **0.16.0+** no longer tracks long-lived trace usage for granular usage reporting ([granular-usage](https://docs.langchain.com/langsmith/granular-usage)).

**Audit log retention:** "Audit logs are retained for up to **400 days**. Events older than 400 days may be removed automatically." ([audit-logs](https://docs.langchain.com/langsmith/audit-logs)).

**Unrelated TTL feature (do not confuse):** `configure-ttl` documents LangGraph **checkpointer** and **store item** TTLs in `langgraph.json` (`checkpointer.ttl` with `strategy: delete | keep_latest`, `store.ttl` with `refresh_on_read`, `sweep_interval_minutes`), plus per-thread TTL overrides and runtime `ttl`/`refresh_ttl` overrides. This governs agent thread state and cross-thread memory, **not** trace retention ([configure-ttl](https://docs.langchain.com/langsmith/configure-ttl)).

**Rate/ingest limits by plan tier** ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)):

| Limit | Developer (no payment) | Developer (payment on file) | Startup/Plus | Enterprise |
|---|---|---|---|---|
| Trace events / hour | 50,000 | 250,000 | 500,000 | Custom |
| Trace data ingest / hour | 500 MB | 2.5 GB | 5.0 GB | Custom |
| Unique traces / month | 5,000 | — | — | — |

Plan tiers referenced across the docs are **Developer**, **Startup/Plus**, and **Enterprise**; the Free tier exists for single-user use ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing), [rbac](https://docs.langchain.com/langsmith/rbac)). Exact list prices are on the marketing pricing page ([usage-and-billing](https://docs.langchain.com/langsmith/usage-and-billing)).
